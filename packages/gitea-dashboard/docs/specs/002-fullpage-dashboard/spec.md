# Feature Specification: Страница Gitea Dashboard во вкладке

**Feature Branch**: `002-fullpage-dashboard`

**Created**: 2026-09-28

**Status**: Draft

## Clarifications

### Session 2026-09-28

- Q: Какие расширения входят в первый выпуск страницы? → A: таблица PR с фильтрами/сортировкой/поиском и история сборок с фильтрами и статистикой. Просмотр логов, карточка репозитория, несколько подключений — позже.
- Q: Нужны ли действия с записью в Gitea? → A: нет, только чтение.

### Session 2026-09-28 (rev.2, после первого просмотра владельцем)

- Q: Вид по умолчанию? → A: табличный: PR — «Таблица», Сборки — «История»; группы остаются переключателем; окно расширения без изменений.
- Q: Как показывать ветки? → A: цветными тегами: `main`/`master` — синий, `test` — жёлтый, прочие — нейтральный.
- Q: Как показывать репозитории? → A: без префикса владельца (`simplx/`), цветным тегом со стабильным цветом на репозиторий; владелец показывается только при совпадении имён у разных владельцев; полное имя — в подсказке.
- Q: Номер PR? → A: отдельной меткой перед тегом репозитория.
- Q: Текущий этап сборки? → A: колонка «Этап» (job › шаг N/M) у выполняющихся запусков + раскрытие строки со списком jobs и шагов; данные только для видимых выполняющихся запусков.
- Q: (rev.3) Группы на странице нужны? → A: нет, только таблицы; переключатель убрать. Статистику истории свернуть по умолчанию. Контент на всю ширину, список репо на всю высоту.
- Q: (rev.3) Можно ли вместо опроса сокеты? → A: нет — у Gitea нет realtime API для Actions (`/user/events` — только по cookie сессии и без статусов сборок); вебхуки требуют своего сервера, что противоречит «без бэкенда». Остаётся опрос.
- Q: (rev.3) Интервал живого обновления? → A: адаптивный: 5 с, пока страница видима и есть мои активные сборки — только активные запуски (1 запрос на организацию) и шаги моих выполняющихся/раскрытых (≤ 3); остальное — 20 с; бюджет ≈ 70 запросов/мин при 3 организациях.
- Q: (rev.3) Настройка цвета репозитория? → A: да, на странице «Репо»: палитра из 8 тонов + «Авто», хранение в storage.sync по `owner/name`, применяется во всех RepoTag; окно не меняется.
- Q: Боковая панель? → A: сворачиваемая до иконок, как канонический shadcn sidebar (collapsible icon), состояние запоминается.

**Input**: User description: "Окно расширения остаётся как есть; в его шапку добавляется кнопка «Открыть во вкладке», которая открывает страницу расширения в новой вкладке (или переключает на уже открытую). Страница — место для расширенного функционала, которого нет в окне: на первом этапе те же разделы (Репо, PR, Сборки) в широкой раскладке, дальше расширения. Живое обновление должно работать и на странице." Зависит от фичи `001-gitea-dashboard` (данные, настройки, подключение, фоновое обновление уже есть).

## User Scenarios & Testing *(mandatory)*

Действующее лицо — **разработчик** с уже настроенным расширением (фича 001).

### User Story 1 — Открыть дашборд во вкладке (Priority: P1)

Разработчик открывает окно расширения, нажимает «Открыть во вкладке» и получает полноэкранную страницу дашборда в новой вкладке. Повторное нажатие не плодит вкладки — браузер переключается на уже открытую.

**Why this priority**: вход в весь расширенный функционал; без него остальное недоступно.

**Independent Test**: из окна нажать кнопку дважды — открыта ровно одна вкладка, фокус на ней; окно расширения работает как прежде.

**Acceptance Scenarios**:

1. **Given** окно расширения открыто, **Then** в шапке есть кнопка «Открыть во вкладке» рядом с кнопкой настроек.
2. **Given** вкладки дашборда нет, **When** нажата кнопка, **Then** открывается новая вкладка с дашбордом и становится активной, окно закрывается.
3. **Given** вкладка дашборда уже открыта (в любом окне браузера), **When** нажата кнопка, **Then** новая вкладка не создаётся — активируется существующая и её окно выводится на передний план.
4. **Given** расширение не настроено, **When** открыта страница, **Then** она показывает то же приглашение открыть настройки, что и окно.
5. **Given** страница открыта, **Then** её можно добавить в закладки и открыть по адресу напрямую.

---

### User Story 2 — Разделы Репо / PR / Сборки в широкой раскладке (Priority: P1)

На странице разработчик видит те же данные, что в окне, но без тесноты: навигация по разделам слева или сверху, списки на всю ширину, больше информации в строке (полные заголовки, все признаки), без обрезки по высоте окна.

**Why this priority**: первый этап страницы; даёт ценность сразу и служит каркасом для расширений.

**Independent Test**: на странице пройти сценарии US2–US4 фичи 001 (поиск репо, группы PR, группы сборок) и убедиться, что данные и поведение совпадают с окном.

**Acceptance Scenarios**:

1. **Given** страница открыта, **Then** есть разделы «Репо», «PR», «Сборки» (и места под будущие разделы), текущий раздел отражён в адресе страницы, так что обновление страницы и «назад» сохраняют раздел.
2. **Given** данные уже получены фоном, **Then** страница показывает их сразу (менее 0,1 с), без ожидания сети.
3. **Given** страница открыта, **Then** сборки обновляются так же часто, как при открытом окне (раз в 15–20 с), и длительность выполняющихся тикает; после закрытия вкладки учащённое обновление прекращается.
4. **Given** ширина окна браузера меньше 1024 px, **Then** раскладка остаётся читаемой (навигация сворачивается, списки не обрезаются по горизонтали).
5. **Given** клавиатура, **Then** работают те же сочетания, что в окне (стрелки, Enter / Cmd+Enter / Shift+Enter в репо, Enter в списках), и переключение разделов по Alt+1..3.

---

### User Story 3 — Таблица PR с фильтрами (Priority: P2)

Разработчику нужно разобрать все открытые PR сразу: отфильтровать по репозиторию, автору, статусу CI, черновикам и конфликтам, отсортировать и найти по тексту — не листая группы.

**Why this priority**: главное преимущество страницы над окном при большом числе PR.

**Independent Test**: при 50+ открытых PR сузить список фильтрами до нужных за несколько кликов; фильтры сохраняются в адресе страницы.

**Acceptance Scenarios**:

1. **Given** раздел PR, **Then** доступен вид «таблица» с колонками: статус CI, заголовок, репозиторий и номер, автор, группа (моё ревью / мой / остальные), признаки черновик/конфликт, обновлён.
2. **Given** таблица, **When** выбраны фильтры (репозиторий — несколько, автор — несколько, статус CI, только черновики / без черновиков, только с конфликтом, группа), **Then** остаются только подходящие строки, а счётчик показывает «N из M».
3. **Given** таблица, **When** введён текст в поиск, **Then** остаются строки, где текст встречается в заголовке, репозитории, номере или авторе (без учёта регистра).
4. **Given** таблица, **When** нажат заголовок колонки, **Then** строки сортируются по ней, повторное нажатие меняет направление; по умолчанию — по времени обновления, новые сверху.
5. **Given** фильтры, сортировка и поиск заданы, **When** страница обновлена или ссылка открыта заново, **Then** они восстановлены из адреса; кнопка «Сбросить» очищает всё.
6. **Given** фильтры не оставили строк, **Then** показано «ничего не найдено» и кнопка сброса.

---

### User Story 4 — История сборок с фильтрами и статистикой (Priority: P2)

Разработчик хочет понять, что происходит со сборками за период: какие workflow и ветки чаще падают, сколько длятся сборки, — и быстро найти нужный запуск.

**Why this priority**: даёт картину, которой нет в окне (там только активные и недавние).

**Independent Test**: за последние 7 дней отфильтровать запуски по workflow и ветке, увидеть долю падений и среднюю длительность, открыть конкретный запуск.

**Acceptance Scenarios**:

1. **Given** раздел «Сборки», **Then** доступен вид «история» — таблица запусков за выбранный период (24 часа / 7 дней / 30 дней, по умолчанию 7 дней) в пределах охвата из настроек.
2. **Given** история, **When** выбраны фильтры (репозиторий, workflow, ветка, событие, итог, «только мои»), **Then** таблица и статистика пересчитываются по отфильтрованным запускам.
3. **Given** отфильтрованные запуски, **Then** над таблицей показаны: всего запусков, доля упавших (%), средняя и медианная длительность завершённых, а также разбивка по workflow (запусков, падений, средняя длительность).
4. **Given** таблица, **Then** строки сортируются по времени начала (новые сверху) или по длительности; клик по строке открывает запуск в Gitea.
5. **Given** запусков за период больше, чем умещается на странице, **Then** работает постраничная подгрузка «показать ещё» без повторной загрузки уже полученных.
6. **Given** фильтры и период, **When** страница обновлена, **Then** они восстановлены из адреса.
7. **Given** история загружается впервые за период, **Then** видно состояние загрузки; повторное открытие того же периода в течение нескольких минут не нагружает Gitea повторно.

---

### User Story 5 — Читаемые теги репозиториев, веток и номеров (Priority: P2)

Разработчик быстро различает репозитории и ветки по цвету, не читая длинные `simplx/…`.

**Acceptance Scenarios**:

1. **Given** таблицы PR, сборок и истории, **Then** репозиторий показан тегом с именем без владельца; одинаковое репо — всегда один цвет; при совпадении имён у разных владельцев показан `владелец/имя`; полное имя в подсказке.
2. **Given** строки сборок и истории, **Then** ветка — тег: `main`/`master` синий, `test` жёлтый, остальные нейтральный.
3. **Given** таблица PR, **Then** номер PR — отдельная метка `#N` перед тегом репозитория.
4. **Given** страница открывается впервые, **Then** PR показаны таблицей, сборки — историей; переключатель на группы работает и запоминается.

---

### User Story 6 — Текущий этап сборки (Priority: P2)

Разработчик видит, на каком job и шаге сейчас идёт сборка, не переходя в Gitea.

**Acceptance Scenarios**:

1. **Given** выполняющийся запуск в разделе «Сборки» или истории, **Then** в колонке «Этап» — имя текущего job и шага и позиция (`build › Run tests · 3/7`); у завершённых — пусто или «—».
2. **Given** строка запуска, **When** её раскрыть, **Then** видны все jobs с их статусом и длительностью и шаги каждого job со статусом, текущий шаг выделен.
3. **Given** страница открыта, **Then** этапы выполняющихся запусков обновляются вместе с живым обновлением; запросы только для видимых выполняющихся запусков, не больше 10 за цикл.
4. **Given** сбой получения шагов, **Then** строка показывает «этап недоступен», таблица работает.

---

### User Story 7 — Сворачиваемая боковая панель (Priority: P3)

**Acceptance Scenarios**:

1. **Given** широкий экран, **When** нажата кнопка сворачивания, **Then** панель сжимается до иконок (с подсказками), контент расширяется; повторное нажатие разворачивает; состояние запоминается между открытиями.

---

### Edge Cases

- Открыто несколько окон браузера и вкладка дашборда в одном из них: кнопка переключает туда, а не создаёт вторую.
- Вкладка дашборда закрыта во время учащённого обновления: учащение прекращается в пределах 10 с.
- Одновременно открыты окно и страница: данные одинаковые, запросов к Gitea не становится вдвое больше.
- Токен отозван или сеть пропала, пока страница открыта: те же состояния, что в окне («токен недействителен», «данные на ЧЧ:ММ»).
- Настройки изменены в другой вкладке: страница подхватывает их без перезагрузки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-101**: Окно расширения MUST сохранить текущее поведение (фича 001) и получить в шапке кнопку «Открыть во вкладке».
- **FR-102**: Кнопка MUST открывать страницу дашборда расширения в новой вкладке, а если такая вкладка уже открыта в любом окне браузера — активировать её и её окно вместо создания новой.
- **FR-103**: Страница MUST быть доступна по постоянному адресу расширения (закладка, прямой переход) и открываться на разделе из адреса; по умолчанию — последний использованный раздел.
- **FR-104**: Страница MUST показывать разделы «Репо», «PR», «Сборки» с теми же данными, группами, статусами, пустыми состояниями и ошибками, что и окно, в широкой раскладке; навигация между разделами MUST быть расширяемой новыми разделами.
- **FR-105**: Страница MUST показывать сохранённые данные мгновенно и получать свежие так же, как окно (внеочередное обновление при открытии).
- **FR-106**: Пока страница открыта, сборки MUST обновляться раз в 15–20 с (как при открытом окне); открытые окно и страница вместе не должны удваивать число запросов к Gitea.
- **FR-107**: Страница MUST поддерживать светлую/тёмную тему по системной настройке, интерфейс только на русском, внешний вид — канонический shadcn/ui (как в фиче 001).
- **FR-108**: Страница MUST работать только на чтение, как вся фича 001: никаких изменяющих действий в Gitea, токен с правами только на чтение.
- **FR-110**: Раздел PR MUST иметь вид «таблица» с фильтрами (репозиторий, автор, статус CI, черновик, конфликт, группа), поиском по тексту, сортировкой по колонкам и счётчиком «N из M»; состояние фильтров хранится в адресе страницы.
- **FR-111**: Раздел «Сборки» MUST иметь вид «история» за период 24 ч / 7 дн / 30 дн с фильтрами (репозиторий, workflow, ветка, событие, итог, только мои), статистикой (всего, доля падений, средняя и медианная длительность, разбивка по workflow) и постраничной подгрузкой; состояние — в адресе страницы.
- **FR-112**: Загрузка истории сборок MUST переиспользовать уже полученные данные и не повторять запросы за тот же период в течение 5 минут; нагрузка на Gitea от открытия истории за 30 дней — не более 20 запросов при охвате по организациям.
- **FR-113**: На странице только табличные виды: PR — таблица, Сборки — история запусков; переключателя «Группы» нет (rev.3).
- **FR-117**: Статистика истории (карточки и «по workflow») по умолчанию свёрнута и раскрывается по клику; состояние запоминается.
- **FR-119**: На странице «Репо» разработчик MUST иметь возможность назначить репозиторию цвет из палитры тегов (или «Авто» — цвет по имени); назначенный цвет используется во всех тегах репозитория на странице и синхронизируется между устройствами разработчика.
- **FR-118**: Контент страницы занимает всю доступную ширину (без ограничения по центру), в т.ч. при свёрнутой панели; список репозиториев занимает всю высоту окна.
- **FR-114**: Репозиторий, ветка и номер PR показываются тегами по правилам US5; цвет тега репозитория детерминирован по имени.
- **FR-115**: Для видимых выполняющихся запусков страница показывает текущий job/шаг (колонка «Этап») и раскрытие строки со всеми jobs и шагами; не более 10 запросов шагов за цикл обновления, только чтение.
- **FR-116**: Боковая панель сворачивается до иконок (канонический shadcn sidebar), состояние запоминается.
- **FR-109**: Раскладка MUST оставаться читаемой на ширине от 768 px и использовать ширину экрана на широких мониторах (без бесконечно растянутых строк — ограничение ширины контента).

### Key Entities

- **Раздел страницы**: идентификатор (repos, prs, builds, …), название, признак «есть в окне»; отражён в адресе страницы.
- **Фильтр таблицы**: набор условий (множества репозиториев/авторов/workflow/веток, статус, флаги, текст, период, сортировка) — сериализуется в адрес страницы.
- **Статистика сборок**: по набору запусков — число, доля падений, средняя/медианная длительность, разбивка по workflow.
- **Вкладка дашборда**: открытая вкладка браузера с адресом страницы расширения; не более одной создаётся кнопкой.
- Данные (PR, сборки, репозитории, настройки, подключение) — из фичи 001 без изменений модели.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: От нажатия «Открыть во вкладке» до видимых данных на странице — менее 1 с.
- **SC-102**: 10 нажатий кнопки подряд оставляют ровно одну вкладку дашборда.
- **SC-103**: Данные на странице и в окне совпадают в 100% проверочных случаев (одни и те же PR, группы, статусы, счётчики).
- **SC-104**: При открытых окне и странице одновременно число запросов к Gitea за 5 минут не больше, чем при открытом одном окне, более чем на 10%.
- **SC-106**: При 200 открытых PR применение фильтра или поиска обновляет таблицу менее чем за 0,2 с.
- **SC-107**: История сборок за 7 дней появляется менее чем за 3 с при первом открытии и мгновенно при повторном в течение 5 минут.
- **SC-105**: Все сценарии фичи 001 для разделов Репо/PR/Сборки проходят и на странице.

## Assumptions

- Страница — часть того же расширения; переиспользует данные фонового обновления, настройки и компоненты фичи 001, новый сервер не нужен.
- Окно расширения остаётся основной быстрой точкой входа; страница — для работы «надолго».
